## 0. The finding that shapes everything

I read the DPG Standard source rather than working from memory. **Indicator 4, Platform Independence:**

> When the digital public good has mandatory dependencies that create more restrictions than the original license, **proving independence from the closed component(s) and/or indicating the existence of functional, open alternatives that can be used without significant changes to the core product is required.**

The assessment questionnaire asks three things, verbatim:

> - Which are the core technologies your solution depends on?
> - Does this solution use any closed components that create proprietary dependency? **For AI systems, please consider dependencies for the code, the model and the data.**
> - How can these closed component(s) be replaced with open alternative(s)? Please provide a list of the active open alternatives and **demonstrate that these closed component(s) can be replaced with those open alternatives with minimal configuration changes, without requiring a major overhaul of the entire system.**

**The Standard does not require you to use open models. It requires you to demonstrate you could, with minimal configuration changes.**

So the work is: turn a hard-coded dependency into a configuration value, ship a tested open-weights configuration as the repository default, and produce CI evidence that both configurations pass the same test suite. Sprints 1 and 2 do exactly that.

## 1. Deployment ladder — the code is identical at every tier

Nepal cannot host GPUs: no machines, no ops staff, and power reliability makes on-prem a liability. That constraint is real and the architecture should respect it rather than argue with it.

But note the distinction that opens the path: **self-hosting the software ≠ hosting the hardware.** Running vLLM on a rented GPU instance in AWS Mumbai is self-hosted for data-control and DPG purposes, with zero hardware in Nepal.

| Tier | What it is | Who sees grievance text | Use it for |
|---|---|---|---|
| **T1 — Hosted inference API** | Hugging Face Inference Providers, Together, Fireworks, DeepInfra | Third-party inference provider | Development, CI, DPG evidence, early pilot |
| **T2 — Your own model instance** ⭐ | vLLM on a rented GPU VM (AWS `ap-south-1` Mumbai, or an Indian provider) under the agency's own contract | Nobody outside the agency's contracted infrastructure | **The production target** |
| **T3 — On-prem** | A box inside the ministry | Nobody | Not Nepal. Possibly Georgia or Uzbekistan later. |

**The only thing that changes between tiers is `LLM_BASE_URL`.** That is the entire point of Sprint 1, and it is also the DPG indicator-4 answer.

**Realistic T2 sizing and cost.** A single 24GB GPU instance (AWS `g5.xlarge` / `g6.xlarge` class, A10G or L4) serves one 27–31B model at 4-bit quantisation to roughly 5–15 concurrent chat users under vLLM's continuous batching, and can co-host Whisper-large-v3-turbo since it's small. On-demand that is roughly **$700–900/month**; a one-year commitment cuts it materially. For a national road-sector GRM's volumes, one instance is very likely enough.

**Two decisions to resolve before committing to T2:**

- **Jurisdiction.** AWS Mumbai is still a cross-border transfer from Nepal. Check it against Nepal's **Individual Privacy Act 2018** and whatever the implementing agency's data terms say. Also worth naming honestly: Nepal–India data flows carry political sensitivity that a Singapore region would not. If the legal read is tight, evaluate Singapore (`ap-southeast-1`) alongside Mumbai — latency to Kathmandu is worse but tolerable for this workload.
- **Who operates it.** A managed instance is a much smaller ops burden than a datacenter, but it is not zero — patching, monitoring, restarts, cost control. Plan for ADB or a vendor to run it initially with a documented handover path, and make "named budget line for run costs" a condition before the pilot converts to production. This is the failure mode that killed Rwanda's Babyl: excellent system, no owner of the running costs.

## Sprint 1 — Make the code LLM-agnostic

**Goal:** every model call routes through a configurable, OpenAI-compatible client. No provider or model name is hard-coded anywhere.

**Why:** it is the DPG indicator-4 answer, it is what lets you move T1 → T2 without a code change, and it insulates you from a market where model prices fall roughly an order of magnitude a year and licences change without notice.

**Files:** `backend/services/llm_client.py` (new), `backend/services/LLM_services.py`, `.env.example`, `docker-compose.yml`

### 1.1 The client factory

```python
# backend/services/llm_client.py
import os
from openai import OpenAI

def get_llm_client() -> OpenAI:
    """
    OpenAI-compatible chat client. Works unchanged against:
      T1  https://router.huggingface.co/v1      (Hugging Face Inference Providers)
      T2  http://<private-ip>:8000/v1           (your vLLM instance)
      T3  http://localhost:8000/v1              (on-prem)
      --  https://api.openai.com/v1             (legacy / comparison)
    """
    return OpenAI(
        api_key=os.getenv("LLM_API_KEY", "not-needed-for-local"),
        base_url=os.getenv("LLM_BASE_URL", "https://router.huggingface.co/v1"),
        timeout=float(os.getenv("LLM_TIMEOUT", "120")),
        max_retries=int(os.getenv("LLM_MAX_RETRIES", "2")),
    )

def get_asr_client() -> OpenAI:
    """Separate: ASR typically runs on a different port or provider than chat."""
    return OpenAI(
        api_key=os.getenv("ASR_API_KEY", "not-needed-for-local"),
        base_url=os.getenv("ASR_BASE_URL", "https://router.huggingface.co/v1"),
        timeout=float(os.getenv("ASR_TIMEOUT", "300")),
    )

MODELS = {
    "classify":  os.getenv("MODEL_CLASSIFY",  "google/gemma-4-31b-it"),
    "extract":   os.getenv("MODEL_EXTRACT",   "google/gemma-4-31b-it"),
    "translate": os.getenv("MODEL_TRANSLATE", "google/gemma-4-31b-it"),
    "asr":       os.getenv("MODEL_ASR",       "openai/whisper-large-v3-turbo"),
}
```

**Make the open configuration the default.** A reviewer who clones the repo and runs it should land on the open path without configuring anything. That is materially stronger indicator-4 evidence than a proprietary default with an open option documented elsewhere.

### 1.3 Convert `json_object` → `json_schema` — the real work in this sprint

Your calls use `response_format={"type": "json_object"}`. Support is uneven across open-weights providers, and open models are less reliable than GPT-4-class at free-form JSON mode.

The fix makes the code *more* robust: an explicit schema with guided decoding constrains generation to the grammar, so output is guaranteed parseable rather than probably parseable.

```python
from pydantic import BaseModel
from typing import Literal, Optional

class GrievanceClassification(BaseModel):
    category: Literal["road_condition", "drainage", "compensation",
                      "safety", "staff_conduct", "other"]
    severity: Literal["low", "medium", "high"]
    district: Optional[str]
    is_duplicate_suspected: bool
    confidence: float

resp = client.chat.completions.create(
    model=MODELS["classify"],
    messages=[...],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "grievance_classification",
            "schema": GrievanceClassification.model_json_schema(),
            "strict": True,
        },
    },
)
result = GrievanceClassification.model_validate_json(resp.choices[0].message.content)
```

Do this for every structured call: classification, contact extraction, content detection. Two to three days, and it removes a class of parsing bugs you are probably absorbing silently today.

Confirm whether that reference is intentional. If it is a typo falling through to an exception handler, you may have a classification path that has been quietly failing.

### 1.5 Degraded mode — do not skip this

**If the model endpoint is unreachable, the chatbot must still accept the grievance and queue it for later classification.** A grievance mechanism that refuses intake because an API is down is worse than one with no AI at all — and in Nepal that is not hypothetical.

You already run Celery and Redis, so the machinery exists. Make the path explicit:

- Intake always writes to PostgreSQL first, before any model call
- Classification is a Celery task with retry and backoff, not an inline blocking call
- Unclassified grievances surface in the officer dashboard as "pending classification", not as errors
- Add a health endpoint that reports LLM reachability separately from application health

Test it by pointing `LLM_BASE_URL` at a dead port and confirming intake still completes.

### 2.2 Speech recognition — the easiest win, with peer-reviewed Nepali evidence

`whisper-1` **is** Whisper. OpenAI hosts a model whose weights are already Apache-2.0, so switching to the open weights is functionally near-identical while removing a closed dependency.

A 2026 comparative study fine-tuned six architectures on the **OpenSLR SLR54 Nepali corpus (~165 hours)**, evaluating on OpenSLR, FLEURS and Common Voice:

| Model | Nepali WER | Licence | Verdict |
|---|---|---|---|
| **Whisper-Large-v3-Turbo** | **14.76%** | Apache-2.0 | ✅ Best-equal, drop-in for `whisper-1` |
| **IndicWav2Vec** (AI4Bharat) | **14.89%** | Verify — AI4Bharat is generally MIT | ✅ Statistically tied, far smaller, CTC decoder much faster |
| MMS-1B | worse | **CC-BY-NC-4.0** | ❌ Cannot ship. Excluded on licence. |
| Whisper-Medium · XLSR-53 · Conformer-Hi | worse | Apache-2.0 | — |

Two takeaways. **~85% word accuracy on Nepali is achievable under Apache-2.0** — usable for grievance intake with on-screen confirmation, and above the threshold where correcting becomes slower than re-entering. And the improvement path is concrete: fine-tuning on SLR54's 165 openly-licensed hours is a single-GPU job, and that fine-tune released openly would be a genuine DPG contribution, because permissively-licensed Nepali speech tooling barely exists.

Also benchmark **Omnilingual ASR** (Apache-2.0, covers Nepali, 300M–7B variants). The 300M model is worth testing specifically for low-connectivity districts.

## Sprint 3 — PII

**Goal:** no personally identifiable information leaves the agency's control — in model calls, logs, or traces.

**Why it's mandatory, not optional:** with self-hosting in Nepal off the table, every tier sends grievance text somewhere else. Redaction is the control that makes that acceptable.

### 3.1 What the current design does and does not cover

Collecting name and contact in structured fields, separately from the narrative, is good design and eliminates the easy version of the problem. Two leaks it structurally cannot close:

**Third-party PII — the sharper exposure.** A road-sector grievance names the site engineer, the contractor, the ward official. Those people never consented to anything. Your complainant consented to give *their* details; nobody asked the engineer whose conduct is described. Different legal category, and asking the complainant separately does nothing about it. For a GRM, complaints naming officials are not an edge case — they are a large share of the useful ones.

**People self-identify in the free-text box anyway.** *"My name is Ram Bahadur, I am from ward 4, and I want to complain about…"* is the most common grievance opening in every system. The **voice channel guarantees it** — nobody speaking naturally observes your field boundaries.

### 3.2 How replacement works mid-sentence

Presidio's analyser returns spans — `(start, end, entity_type, score)` — and the anonymiser rewrites in place, right-to-left so earlier offsets don't shift. Three choices matter:

- **Placeholders, not deletion.** `<PERSON_1>`, not removal. The sentence keeps its grammatical shape so the classifier still parses it. Deleting words degrades classification noticeably; substituting a token barely does.
- **Consistent mapping within a document.** Same name → same token: *"`<PERSON_1>` promised to fix it, then `<PERSON_1>` refused to return."* Fresh tokens per occurrence destroy exactly the narrative structure the classifier uses.
- **Reversible where the officer needs the original.** Presidio's anonymiser supports encryption with a key, not only redaction. Keep two representations: the full record for officer action, the redacted derivative for model calls and logs. **Redact before transmission, never before storage.**

### 3.3 Nepali specifics — where the standard tooling fails

**Devanagari digits will defeat your phone regex.** Nepali users type `९८४१२३४५६७`. An ASCII `\d` pattern misses it completely — and that is a phone number sitting in plain text heading to a third party. **Normalise ०–९ → 0–9 before pattern matching, or match both character classes.** Probably the single highest-value line of code in the filter, and exactly the kind of thing that passes every test written by an English speaker.

```python
DEVANAGARI_DIGITS = str.maketrans("०१२३४५६७८९", "0123456789")
normalised = text.translate(DEVANAGARI_DIGITS)
```

Write custom recognisers for: `+977`, ten-digit mobiles on `97x`/`98x` prefixes, landline area codes, citizenship certificate numbers.

**Person-name detection is the hard part.** spaCy ships no trained Nepali NER pipeline, so Presidio's defaults find nothing in Devanagari. Deny lists of names are weak here — the Nepali name space is large and many given names double as common nouns, giving poor recall *and* poor precision.

The working route is Presidio's **transformers NLP engine**, configured per language with `model_to_presidio_entity_mapping` (`PER → PERSON`, `LOC → LOCATION`, `ORG → ORGANIZATION`). A Nepali XLM-RoBERTa NER fine-tune exists, reporting **PER F1 0.87**, overall F1 0.79.

⚠️ Two caveats, both material:
- **Its licence is not stated** on the model card — an indicator-2 and indicator-4 problem for a DPG submission. Resolve it with the author or fine-tune your own on an openly-licensed corpus.
- **It is trained on WikiANN** — Wikipedia prose, not colloquial spoken grievances transcribed from voice. Expect meaningfully worse than 0.87 on real traffic. Measure on your own data.

**Tune for recall, not precision.** A missed name is a privacy breach; an over-redacted common noun is a small classification quality hit. Set the score threshold low and accept false positives.

**Do not redact LOCATION** if your classifier derives district from the narrative — you will break your own pipeline. Either leave LOC intact (a district name alone is not identifying) or take district from the structured field and redact freely.

### 3.4 The leak that actually happens

The model call is the leak everyone designs against. **Logs and traces are the leak that actually occurs.**

Langfuse traces, application logs, exception reports carrying request bodies, Celery task payloads sitting in Redis, database backups shipped offsite, analytics exports. These get copied, attached to bug reports, pasted into chat, and stored on third-party infrastructure far more casually than any API call.

So place redaction at the boundary of the **logging and tracing layer** as well as the model client:

- A logging filter that redacts before anything is written
- Verify your observability configuration is not capturing full prompt bodies containing grievance text
- Check what Celery serialises into Redis, and Redis persistence settings
- Confirm database backup destinations and their jurisdiction

### 3.5 Module to build

`backend/services/pii_service.py`:

- Devanagari digit normalisation
- Custom recognisers: Nepali mobile, landline, citizenship number, email
- Presidio transformers NLP engine wired to a Nepali NER model
- Consistent, reversible placeholder mapping with per-document scope
- `redact_for_model(text) -> (redacted, mapping)` and `restore(text, mapping)`
- A logging filter applying the same redaction
- A test set of realistic Nepali grievance strings, including Devanagari-digit phone numbers and third-party names, asserting recall
